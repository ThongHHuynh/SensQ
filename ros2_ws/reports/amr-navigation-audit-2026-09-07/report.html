Assessment

The repository has a meaningful working foundation: Nav2 point-to-point navigation, AMCL/EKF, SLAM configuration, a custom docking action, reusable docking geometry, visual anchoring, bounded retries, reverse approach, station recording and coverage execution. It should not yet be treated as a qualified unattended AMR platform.

The highest-risk gaps sit at subsystem boundaries: lost commands can release the wrong motion source, invalid sensing can look clear, the collision model excludes overhang, and encoder feedback loss does not stop the interface. Docking success currently means an estimated pose was held; it does not establish physical engagement or charging.

Recommended order: fix protective motion and hardware fault handling → stabilize navigation/mapping → develop verified docking/charging/undocking → add durable transport missions → integrate lift/drop.

P0 = block unattended operation until resolved and verified. P1 = required for the reliable platform lifecycle. P2 = hardening, consistency or maintainability. These priorities are engineering judgments, not a measured safety classification or certification.

Command and state architecture

Current supported hardware navigation path

Nav2 controller→/cmd_vel_nav→Velocity smoother→/cmd_vel→Velocity arbiter→/cmd_vel_out→diff_drive_controller→Serial driver / MCU

Docking publishes /cmd_vel_dock into the arbiter at higher freshness priority. The installed Nav2 behavior server publishes to /cmd_vel through its unremapped command output, so recovery commands join downstream of navigation smoothing. The proposed final protective stop must cover every motion source.

Hardware TF ownership is structurally correct in my_robot_navigation/bringup.launch.py: AMCL owns map → odom, EKF owns odom → base_footprint, and robot_state_publisher owns the sensor/joint tree. The mapping launch does not establish the same contract (N02).

Simulation uses the Gazebo drive/bridge path and a simulation EKF, rather than the physical serial/ros2_control path. Passing simulation does not test firmware, electrical contact or real braking.

Target operational lifecycle

BOOT / SELF-CHECK→LOCALIZED / READY→MISSION→DOCK / CONTACT→CHARGE VERIFIED→UNDOCK→READY

Every motion state needs a transition to a latched stopped/fault state. Manual recovery must re-establish readiness before resuming. A mission manager owns the job; a motion supervisor owns command authority; charger and lift managers own their respective interlocks.

Docking sequence actually implemented

Optional Nav2 predock → tag search → corridor entry/alignment/run → pose hold → success. Tag failures may trigger bounded backup/rotation/reacquisition. Reverse mode shortens the blind entry by using staging distance. The current server does not execute the separate staging verification phases described in README as distinct orchestrated stages.

Keep: database validation and atomic recording; rejection of overlapping Dock goals; timestamp-matched tag TF; bounded timeouts/retries; acceleration-limited dock commands; stop calls on exceptions/finalization; controller tests; RViz trails. Strengthen their integration rather than replacing the entire stack.

P0 D01 · Confirmed code behavior

Obstacle checks are bypassed near the dock

The corridor controller returns no directional safety fault whenever tag distance is within target_distance + dock_contact_distance. Hardware stations use a 0.30 m final distance and the band is 0.15 m, so the exemption begins at 0.45 m from the tag. It exempts any obstacle in that sector, without identifying the dock surface. Rotations also exclude a ±0.60 rad sector around the tag. The 0.10 m minimum tag distance cannot detect an intervening object. The same helper also handles retreat motion.

Improve: Replace broad sector exemptions with a bounded, station-specific contact envelope and validated dock-surface filtering. Keep unrelated obstacles and the swept robot footprint protected during entry, turning, reverse and retreat. Add a final protective stop path downstream of motion arbitration; independent hardware protection must remain effective during intended contact.

Acceptance: Inject obstacles beside and directly between robot and dock at every phase, including inside the contact band and rotation exclusion. Each must prevent contact with the obstacle. Verify the intended dock remains reachable.

P0 D02 · Confirmed code behavior; trigger requires concurrent Nav2 traffic

Docking command loss can release control back to navigation

The arbiter selects docking only while its last Twist is fresh; after 0.25 s it selects fresh navigation traffic. There is no docking ownership lease, latched fault, or docked/charging inhibit. A docking crash, hang, completed goal or safety abort can therefore expose another active navigation publisher. A final zero Twist only holds priority briefly.

Improve: Introduce explicit motion ownership and a latched safe-stop state. Loss of the active owner must stop the base until an authorized state transition releases it. Serialize navigation, docking, coverage and teleoperation; reject non-finite commands and use a monotonic watchdog for hardware motion.

Acceptance: Keep a navigation command stream active while killing or stalling docking and while canceling or completing a dock goal. Output must stay zero until ownership is explicitly transferred. Test clock jumps and invalid Twist values.

The diff-drive YAML sets linear/angular maximum values but omits has_velocity_limits, which defaults to false in installed diff_drive_controller 2.53.3. P0 H02 · Confirmed code behavior

Lost encoder feedback does not fault the drive interface

Hardware read() returns OK with no valid count packets and retains previous state. Serial read errors are converted to zero bytes. There is no age deadline for valid encoder frames, sequence number or MCU reset detection. If host writes continue while telemetry is lost, firmware command timeout alone does not address the failure. Invalid data without newlines can grow the receive buffer.

Improve: Add a bounded parser, valid-packet watchdog, reset/sequence detection, plausibility checks and a fault state that inhibits motor commands. Timestamp samples; use actual sample intervals for velocity. The current per-controller-period velocity calculation is inaccurate for delayed/batched packets, although position feedback is the default odometry input.

Acceptance: Drop telemetry while continuing command writes, inject corrupt/truncated frames, and reset the MCU with nonzero encoder totals. Fault and stop within the commissioned deadline; prevent odometry jumps and require deliberate recovery.

P1 D04 · Confirmed timing mismatch; physical error unmeasured

Tag anchoring combines measurements from different times

TagTracker obtains base-to-tag at the image timestamp, but docking transforms that pose with the latest odometry pose. A moving robot therefore builds an inconsistent odom-frame anchor. The running blend can also apply the same detection repeatedly, making smoothing depend on controller rate. Initial acquisition deduplicates timestamps but accepts fewer than anchor_samples when its timeout expires.

Improve: Obtain odom-to-tag at the detection timestamp or interpolate odometry to that time. Blend each observation once; gate position/yaw innovations, observation quality and minimum independent samples. Track anchor uncertainty and age explicitly.

Acceptance: Replay delayed camera data while translating and rotating past a stationary tag. Its odom-frame pose should remain stable within the allocated error budget. Duplicate frames must not change filtering weight.

Development roadmap
Use evidence-based exit gates rather than calendar estimates. Staffing, the charger/BMS choice, payload geometry and physical performance were not provided, so effort estimates would be premature.
Gate 0 · Establish a protected, deterministic base
P0 findings D01/D02/N01/H01/H02 plus R03

Exit criterion: Do not advance to unattended trials until every injected loss of authority, sensing or communication produces the validated safe response.
Gate 1 · Reliable navigation and mapping
N02/N03/N04/N05, H03 and R01
One supported bringup, readiness supervisor, localization recovery, map save/load/versioning, consistent control limits and green CI.
Exit criterion: Point-to-point and mapping acceptance matrix passes across allowed starts, obstacles, payloads and restarts.
Gate 2 · Verified docking and charging
D03–D08; depends on Gate 0 and stable odometry
Time-aligned perception; contact-confirmed dock; BMS/charger integration; bounded reseating; undocking and charging inhibit.
Exit criterion: Reach and leave the real dock repeatedly; never claim charge success with missing electrical evidence; faults remain stopped.
Gate 3 · Autonomous transport operation
R02; depends on Gates 1–2
Durable job manager, station/map registry, low-energy return, operator UI/status, event history and supervised resume.
Exit criterion: A full-shift mission trial plus reboot/fault scenarios preserves jobs and package state and reports every unresolved fault.
Gate 4 · Lift/drop and package deposit
Requires stable station approach and mission transactions
Add action-based actuator control, homing, upper/lower limits, overload/jam detection, package presence and release confirmation.
Exit criterion: Test empty pickup, jam, overload, power loss mid-lift and failed release. Navigation must obey lift/load interlocks; deposit succeeds only on sensor-confirmed transfer.
Design the lift/drop contract now; implement after the base is stable
Reserve actions for home, lift and lower, with progress, cancellation and typed faults. Define upper/lower limits, position, actuator current, package presence and load state. Agree what “safe to drive” means at each lift position, including braking and power loss. Couple speed and footprint to payload state.
Deposit should be a transaction: arrive at the correct station → verify station ready and robot stopped → lower/release → confirm package transfer → confirm lift clear → retreat → complete the job. A timeout or commanded actuator movement is not proof of transfer. A later PLC or station interface can provide the external handshake.
Operational features needed alongside missions
Add a station registry tied to map identity/version, restricted and speed zones, durable mission events, health/status UI, actionable fault codes, log/rosbag capture around faults, configuration provenance, pinned dependencies, deployment rollback and boot supervision. Namespacing and access control should prevent unintended command publishers as the platform grows. Fleet scheduling can follow once single-robot mission recovery is reliable.
